# 是否接入 Jev 类决策模型：评估（2026-10-12）

## 结论
**游戏本身不接入。研究上可以留一个低成本的离线对照实验，排在最后，做不做都行。**

## 依据

### 1. 现有方案已经够用，Jev 能带来的收益有限
| 维度 | 现状（Gemini 3.1 Flash-Lite + 引擎） | Jev 能改善多少 |
|---|---|---|
| 准确率 | test 84.6%（dev 92.8%） | 未知。NeoHorse-Jev-4B 的 77.70 分是开发方自己汇总的，任务和我们不同，也没有日语数据 |
| 有害误触发 | test 1.0%（dev 0.5%） | 即使降到 0，也只差 1 个百分点 |
| 状态安全 | S4 = 0，由引擎保证，和用什么模型无关 | 无 |
| 延迟 | p50 约 1.0–1.2 s | 能降到 0.1 s 以内，但回合制游戏里 1 秒本来就能接受，而且很多回合之后还要再调用一次叙述 |
| 成本 | 约 $0.0003/回合 | 本地运行是 0，但要一直开着 GPU |

### 2. 和我们的任务形态不匹配
- 我们的 plan 由 6 个相互关联的字段组成（kind、action_id、operation、target_id、item_id、advance），dialogue/clarify 还需要**生成**一句 `reply`。Jev 只能从预设选项里挑，生成不了文字。
- 拆成多个 Choice 问题时，Jev 的各个问题**互相看不到彼此的答案**，可能出现"kind 选了 dialogue、action 却选了攻击"这类组合不一致。这正是本地小模型已经暴露的失败方式（conflict 100%）。
- 说到底，仍然需要一个生成模型来写回复，Jev 只能替掉其中一部分。

### 3. 接入成本高，不确定性大
- NeoHorse-Jev-4B 要用 vLLM、SGLang 或它自带的运行时，不支持 Ollama。在这台 Windows 机器上很可能要走 WSL；RTX 4060 只有 8 GB 显存，4B 模型不量化放不下，量化后效果没有数据。
- TypeSafe Jev 是闭源 API，要排队申请，数据只在美国处理，长期可用性不明。
- 没有任何日语表现的数据。

### 4. 非文字输出也不需要它
表情、BGM、震屏这类"演出"，大部分可以由引擎按事件确定（命中就震屏，换场景就换背景和 BGM）。少数需要理解语义的，例如 NPC 的表情，让叙述模型在同一次回复里顺带输出一个枚举字段就够了，不用额外调一个模型。

## 如果以后要做研究对照（可选，排在最后）
1. **零成本基线**：不接 Jev，用现有的 Ollama 模型，对每个候选 plan 计算对数似然打分（"给候选打分"而不是"生成"），在 v2 dev 上和现在的生成方式对比。看的是准确率、校准程度（ECE）、低置信度时转 clarify 的效果。
2. 只有第 1 步显示"打分 + 置信度阈值"明显优于生成，才值得在 WSL 上部署 NeoHorse-Jev-4B 做第二组对照。
3. 这项实验可以独立成论文里的一节："决策模型与生成模型做 GM 裁定的对比"。不影响游戏。
