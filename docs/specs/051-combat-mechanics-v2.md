## 1. G1 命中与闪避（dex 推导）

### 1.1 现状
`host/combat.py` 的 `_resolve_attack`：`命中率 = clamp(accuracy − evade − 攻击者状态的 accuracy_penalty, 5, 100)`，`true_damage` 恒为 100；`evade` 取受击者 `combat.evade` 的固定值（勇者 0、魔法使い 2、盗賊 8，敌人各自的固定值）。同伴的 `damage_enemy` 也走这条路径（accuracy 写死 100）。

### 1.2 新机制（均由规则开关控制）
- `combat_rules.evade_model`：`"fixed"`（现状，默认，取 `combat.evade`）或 `"dex"`。
- `combat_rules.evade_formula`（仅 `dex` 模型用）：`{"base": 4, "per_dex": 1.5, "cap": 20}`，闪避% = `clamp(round((dex − base) × per_dex), 0, cap)`。这是设计文档 G1 里 AGI 公式换成现有属性 **`dex`**（本项目没有 `agi`）；系数只是起始值，由设计负责人在 normal 覆盖层里调。
- **玩家和敌人都用同一公式**，以各自当前 `attributes.dex`（含升级成长）计算；敌人可在 `combat.evade_cap` 单独设上限（默认同公式）。
- 临时闪避加成（技能、道具、状态）另算：总闪避上限 40%，单个加成持续不超过 2 回合；上限常量放规则里。
- `combat_rules.enemy_accuracy_override`：`null`（现状）或整数（normal 将设为 100）。设置后，**敌方所有攻击能力**的基础命中取该值；`accuracy_penalty` 类状态（烟幕、致盲）、`true_damage` 照旧生效。命中率下限仍为 5%。
- 命中率 = `override(或能力自带 accuracy) − 总闪避 − 命中惩罚`，clamp 到 [5, 100]。
- 凡是向玩家展示或向模型提供命中 / 闪避数值的地方（战斗 UI 的提示、`scenario_context` 的角色信息、战斗日志里的 `chance`）都要同步用新口径；没有这类展示就不新增。
- 里程碑成长里 dex 的增长是数值，不在本任务；盗賊现有 dex 成长保持。

### 1.3 报告项（不要调系数）
汇报里列一张表：四职业（勇者、僧侶、魔法使い、盗賊）在 Lv1 与满级里程碑时的 dex、闪避%（`dex` 模型、起始系数）；设计目标是勇者 Lv1 2–5%、僧侶 2–5%、魔法使い 4–6%、盗賊 12–15% 且满级 20%。**偏差较大的（预计僧侶、盗賊）如实写出，由设计负责人调系数或 dex 成长。**再列出 56 个敌人里闪避最高的 10 个。

## 2. G3 冷却机制与"免费致死保护"

### 2.1 引擎没有冷却，要新增（`grep cooldown host/*.py` 为空）
- 技能 / 道具数据增加 `cooldown: N`（整数 ≥ 1）：使用后，玩家接下来的 N 个**回合**不能再选它；战斗开始时全部冷却清零；冷却在回合结束时递减。
- 战斗 UI 里冷却中的行动灰显并写明剩余回合（文字单份，如「あとNラウンド」，用占位前缀 `【仮】`，列进汇报由设计负责人定稿）。服务端同样拒绝冷却中的使用（不能只靠 UI），自由行动路径映射到该技能时也要被拒绝并给出同样原因。
- 同伴 / 敌人的能力是否也需要冷却：现有 AI 权重足够，本任务不做；若敌人技能数据里已有类似字段，沿用并说明。

### 2.2 神聖の庇護
- normal 覆盖层给勇者的 `divine_guard` 加 `cooldown: 1`（baby 不加）。设计意图：用完下一回合不能再用，所以没法每回合都防御。
- **通用规则审计**：写一个测试遍历所有带 `survive_at_one`（致死保留 1 HP）的技能 / 道具 / 状态，要求在**有效 normal 包**里每一个都带 `cooldown ≥ 1` 或有资源消耗（`cost > 0`）。已知满足的：不屈の構え（2 SP）、影隠れ・改（2 SP）、聖なる守護（6 MP）；`divine_guard` 由上面的覆盖层满足。
- 同时核对**是否还有别的零成本无限致死保护路径**（例如普通防御指令、装备、同伴效果），有则列进汇报，不要擅自改。baby 在这条审计里允许失败，测试对 baby 只要求"与冻结一致"。

## 3. 状态效果系统
### 3.1 数据格式
剧本包新增 `status_defs`（两份同步），每项：
```json
{
  "id": "burn", "name": "灼熱", "icon": "burn",
  "kind": "dot",
  "stackable": false, "max_stacks": 1,
  "duration": 3,
  "tick": {"damage": "1d4", "element": "fire", "ignore_defense": true},
  "modifiers": {},
  "cleansable": true,
  "tags": ["fire", "debuff"]
}
```
- `kind`：`dot`（回合末伤害）、`modifier`（改变属性或数值）、`skip_turn`（失去行动）。
- `modifiers` 支持：`damage_dealt_multiplier`（弱化）、`accuracy_penalty`（已有）、`evade_bonus`（可为负）、`received_damage_multiplier`、`skip_chance`（麻痹：每回合以该概率失去行动）。
- 持续：`duration` 以受影响者自己的回合末递减；重复施加时刷新持续时间；`stackable` 的状态叠层（`max_stacks` 为上限），伤害 = 层数 × 每层 `tick`。
- 抗性：敌人数据可写 `status_immunity: ["stun", ...]`；**Boss 对眩晕默认免疫**（`encounter_class: boss` 且未显式允许时）。玩家侧不设抗性。
- 清除：`cleanse` 效果 `{ "cleanse": {"count": 1 | "all", "tags": ["debuff"]} }`，只清除 `cleansable` 的状态；僧侶的净化类技能用它（技能本身在另一个 spec，这里提供效果和测试用的最小技能）。

### 3.2 必须实现的状态（数值全部是占位起始值，由设计负责人调；我给的只是格式示例）
| id | 暂定日文名 | 说明 |
|---|---|---|
| `burn` | 灼熱 | 火系敌人攻击附带；回合末火属性伤害；不叠层，刷新时长 |
| `poison` | 毒 | 带毒敌人、スライム王；**可叠层**（`max_stacks` 5），伤害 = 层数 × 每层 |
| `weaken` | 弱体 | 造成的伤害 ×(1−x) |
| `paralysis` | 麻痺 | 每回合以概率失去行动 |
| `stun` | 気絶 | 失去 1 个行动；Boss 免疫（见上） |
- 日文名是暂定，用 `【仮】` 之外的正常字符串即可，设计负责人会在汇报后确认 / 改名。`docs/design/skills-v2.md` 第 4 节若列出更多状态（例如圣印、流血、致盲、神速、护盾、再生），按同一数据格式实现；每种在 `status_defs` 里只加定义，不写具体技能。
- 状态附加方式：能力（敌人技能、玩家技能、道具）的 `on_hit_status` 已存在，扩展为支持 `chance`（附加概率，默认 100）、`target`（`target` / `self`）、`stacks`。命中并造成伤害后才结算（现有语义不变）。
- **玩家身上的状态**：现在只有敌人有逐回合结算（`_tick_enemy_statuses`）；玩家需要同样的结算顺序、日志（沿用 `status` / `status_damage` 日志类型，不新增叙事类型）、战斗结束时清除。
- 非战斗中附加的状态（来自第 5 节的陷阱）：默认规则——保留到下一场战斗开始时生效并开始计回合，休息或战斗结束清除。你认为不合适就写明替代方案，但不要扩大范围。
- 战斗 UI：双方的状态以小标签显示（图标 + 名称 + 层数 + 剩余回合），悬停 / 点击显示说明文字；说明文单份，来自 `status_defs.description`（占位 `【仮】`）。图标用现有素材或简单的文字符号占位，**不生成新美术**，缺的素材列进汇报。
- 模型侧：不改默认 prompt。新增日志仍用现有类型，确认叙述上下文不会因为多出状态条目而缺字段或报错。

### 3.3 启用方式
- 敌人技能附带状态属于数据，由设计负责人决定哪些敌人带什么状态后单独下发（写进 normal 覆盖层）。**本任务不给剧本里的任何敌人加状态**；机制用测试夹具里的假敌人验证。
- 本任务写入剧本 normal 覆盖层的内容**仅限**下面这份清单（baby 一律不动）：
  1. `combat_rules.evade_model = "dex"` 与 `evade_formula`（起始系数）；
  2. `combat_rules.enemy_accuracy_override = 100`；
  3. `divine_guard.cooldown = 1`；
  4. `ice_charm.requires_target_weakness = "ice"`；
  5. `fire_bat_dragon` 的 `round_start_effects` 改为按伤害挂钩的回复。
  另外 `status_defs` 是新增定义（不是数值覆盖），放基础包，对 baby 无影响（没有任何东西引用它们）。

## 4. B1 氷の護符只对冰弱点目标可用
- 道具 `ice_charm`（战斗数据 `kind: damage`，`element: ice`，不消耗）增加字段 `requires_target_weakness: "ice"`（通用字段，其他道具以后可用）：目标当前对该元素的抗性倍率 `> 1` 才可使用。字段只在 normal 覆盖层给 `ice_charm`。
- 多敌人战斗：选择的目标满足即可；没有任何可选目标满足时整个行动灰显。
- **按"当前"抗性判断**：虹晶樹每 2 回合轮换抗性，要读取当前阶段（只有"紅"阶段可用）；状态或事件临时改变抗性也算。
- UI：战斗行动列表里灰显并说明原因（单份文字，占位 `【仮】`，如「氷に弱い相手にしか使えない」）。**服务端同样拒绝**，自由行动路径映射到它时给出同样原因，不能被文字输入绕过。
- 不改 `activated_ice_charm`（锻造后的追击）：设计文档没有提到它，保持原样，并在汇报里写明"是否也需要同样限制"留给设计负责人。
- 汇报里列出现在能用护符的对象（设计文档 B1 的清单：熱岩トカゲ、炎のウィスプ、紅晶ゴーレム、ファイアスライム、火の精霊、虹晶樹（紅）、イグニス、ザンザスの分身、飛竜ノクス），用引擎实际读出来的结果对照，不一致的指出。

## 5. B3 火コウモリ竜：回复 = 实际火伤 × 比例
- 现状：`companions[fire_bat_dragon].round_start_effects` 是 `damage_enemy`（2d3 火）加固定 `heal_player`（3，`fire_bat_empowered` 后 6）。
- 新机制：`heal_player` 支持 `scale_from_damage: {"source": "previous_damage_enemy", "ratio": 0.75}`，回复量 = 同一同伴本回合 `damage_enemy` **实际造成的伤害**（已含抗性、防御、命中结果）× ratio，取整规则：四舍五入，最低 0。强化后 ratio 1.5（用 `requirements: {flag: fire_bat_empowered}` 的第二项表达，和现状一致）。
- 未命中、伤害为 0、或目标对该元素的抗性倍率 `< 1`（火抗）时**不回复**。
- 为此 `_resolve_attack` 需要把"实际造成的伤害"传出来（现在是 `None` 返回值）；改的时候不能改变任何既有的伤害 / 日志行为。
- 同伴的 `damage_enemy` 目前写死 accuracy 100、仍然受目标闪避影响：在 `dex` 闪避模型下，敌人闪避会让它偶尔落空——这是预期；汇报里写明。
- 数据：只在 normal 覆盖层改 `fire_bat_dragon` 的 `round_start_effects`（baby 保持固定 3 / 6）。
- 可选项（设计文档里标"可选"，**本任务不做**）：攻击目标优先火弱点。
- 对普通敌人的期望：2d3 平均 4，×0.75 ≈ 3；强化 ≈ 6——与现状基本持平。汇报里用 N=2000 的模拟给出普通敌人与火抗敌人下的每回合平均回复。

## 6. 非战斗陷阱与落石（机制与格式）
- 在地点行动上标记 `hazard`（只是标签，供工具统计与客户端提示）：
  ```json
  {"id": "...", "text": "...", "hazard": {"kind": "trap" | "rockfall", "warning": "..."},
   "roll": {"dice_type": "1d20+dex", "dc": 10, "skill": "<040 的技能名>"},
   "failure_effects": [{"damage_player": {"max_hp_ratio": 0.15}}, {"apply_status": "poison"}],
   "success_effects": []}
  ```
  判定沿用 040 的格式（`skill`、修正值、优势 / 劣势），不新增判定类型。
- 新效果：`damage_player`（支持 `dice`、`max_hp_ratio`、`flat`；致死时的处理：**非战斗伤害不致死**，至少留 1 HP，并在汇报里说明；若现有 `hp` 类效果已是如此则沿用）、`apply_status`（见第 3 节）。先核对现有 `failure_effects` 是否已能扣 HP（`class_aware.failure_hp_change` 暗示已有），能复用就不要造新名字。
- 陷阱的发现 / 规避手段由判定、职业技能（例如盗賊的熟练）和道具（后续）承担，本任务只保证数据格式支持：同一个行动可以用 `visible_for_character` / `requirements` 给特定职业提供"解除"选项。
- **具体放在哪些场景、数值、文本由设计负责人在附录 A 补充**；附录没填之前，本任务不往剧本里加任何陷阱，只用测试夹具验证。
- 离线 / 模拟工具若按行动枚举判定，需要识别 `hazard`：列进汇报，不要改 `scripts/balance/`。

## 7. 商店主动道具（机制与格式）
- 主动道具 = 战斗中使用的 `combat` 道具。核对现有 `item_mechanics.py` / `combat.py` 能否表达下列效果，缺口补上（数据驱动，不为单个道具写死逻辑）：单体 / 全体伤害（`all_targets` 已有）、附加状态（第 3 节 `on_hit_status`）、清除状态（`cleanse`）、临时增益（防御倍率、闪避加成，遵守第 1.2 节的上限）、一次性目标限制（`requires_target_weakness`）。
- 商店条目沿用现有 `shops` 结构。**新增实体（道具、上架条目）按 047 的规则不能放在覆盖层里**，而放进基础包又会让 baby 也买到新道具，与"baby 冻结"冲突。所以本任务**只提供格式和测试夹具，不往剧本里新增任何商店条目 / 道具**。具体道具清单由设计负责人在附录 B 补充后另发 spec。
- 请在汇报里评估候选方案：给商店条目加可见性字段（例如 `difficulty_only: ["normal"]`，经 047 的机制开关通道支持），写明需要改哪些位置（`shops.py`、`scenario_context`、客户端商店界面、冻结快照测试）以及风险。
