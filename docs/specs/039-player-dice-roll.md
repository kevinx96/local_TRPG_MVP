# 039 玩家亲手掷骰与非战斗判定动画

来源：用户（2026-10-19）：提高 D&D／TRPG 感。现在判定在服务器里自动掷完，界面只显示一个写着合计值的静态圆圈，玩家从来不"自己掷骰"。本任务只做非战斗判定的呈现，战斗不在范围内。日文为定稿文本，照抄。

后续任务会改修正值公式（D&D 式 (属性−10)÷2 + 熟练）、给判定加技能名、加优势/劣势。本任务的判定信息必须由引擎里**和实际掷骰同一个函数**算出来，后续改公式时界面自动跟着变，不要在客户端或别处另算一遍。

## 1. 选项上的判定信息（服务器）
- 带 `roll` 的选项在公开的 choices 里多一个 `check` 字段：
  `{"dice": "1d20", "attribute": "dex", "attribute_label": "敏捷", "modifier": 5, "dc": 14}`
  - `dc` 是按当前会话套用 `dc_overrides` 之后的值（`action_dice_settings`）。
  - `modifier` 与 `roll_dice` 实际加上的值一致（现在是属性原值）。没有属性的 `1d20` 判定 `attribute` 为空、`modifier` 为 0。
  - 属性显示名：str 筋力、dex 敏捷、int 知力、wis 知恵、end 耐久。
- DC ≥ 100 的必败判定（现有 3 个）不出 `check`，按现状处理。
- 「？？？」选项不出 `check`（不能泄露任何信息）。
- 自由输入不能事先知道判定，不出 `check`。

## 2. 掷骰前的判定卡（客户端）
- 点击带 `check` 的选项后**先不发请求**，在对话框上方显示判定卡：
  - 标题：选项文字
  - 一行：`敏捷判定　DC 14`
  - 一行：`1d20 ＋ 5（敏捷）`
  - 按钮：「ダイスを振る」（主按钮）、「やめる」（回到选项，不发请求）
- 「ダイスを振る」之后才发送 turn 请求，同时开始播放掷骰动画（第 3 节）。
- 键盘：Enter／空格＝振る，Esc＝やめる。

## 3. 掷骰动画
- 画一个 d20（SVG 二十面体轮廓，金色，沿用现有 CSS 变量），翻滚并快速切换数字。
- 有判定卡时：动画一直转到请求返回，最少转 0.9 秒；返回后停在**自然点数**（`rolls[0]`），再依次显示「＋5 ＝ 19」和「DC 14　成功／失敗」。
- 大成功（自然 20）：金色闪光，并显示「大成功」；大失败（自然 1）：红色碎裂效果，并显示「大失敗」。
- 没有判定卡的情况（自由输入或其他途径产生的新判定）：返回后播放 0.6 秒的短版动画，再显示同样的结果。
- 结果停留约 1.2 秒后收起，再显示叙述和下一组选项。点击任意处跳过动画、直接看结果。
- `prefers-reduced-motion` 时不翻滚，直接显示结果。
- 收起后，现有的骰子横幅照常保留最近一次结果，作为摘要。
- 战斗中不出现判定卡和动画（战斗沿用现有演出）。
- 请求失败时动画停止、收起判定卡，按现有方式显示错误，选项恢复可点。

## 4. 不做什么
- 骰子永远由服务器掷。不使用 `TurnRequest.client_dice` / `roll_dice(client_rolls=...)`，也不新增任何由客户端决定点数的途径。
- 不改任何 DC、属性、修正值，不改剧本数据和 prompt。
- 不碰 `host/prompt/processed/`、`eval/benchmark/`、`docs/`（设计负责人同时在改剧本，避免冲突）。

## 5. 验收
- 单元测试：公开的 choices 里带 `check` 且数值正确（含一个 `dc_overrides` 生效的例子、一个无属性 `1d20` 的例子）；DC999 和「？？？」选项没有 `check`。
- `python -m unittest discover -s tests -q`、`node --check client/app.js` 通过。
- 更新 `client/index.html` 的 `?v=` 缓存键。

## 6. 汇报
- 改了哪些文件；判定信息由哪个函数算出；动画各阶段的时长。
- 有没有发现会让判定卡显示的 DC／修正值与实际掷骰不一致的情况。
