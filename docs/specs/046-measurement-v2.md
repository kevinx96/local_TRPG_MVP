# 046 测量 v2：玩家原型、决策敏感度指标与人类试玩遥测（阶段 A）

来源：用户（2026-10-20）人类试玩（exe 打包版，勇者）几乎没动脑就通关，包括邪竜イグニス；设计负责人据此写了 `docs/design/balance-v2-decision-metrics.md`（r5，主要决定已确认）。本 spec 是该文档第 4 节 **A 阶段（测量先行）**的全部内容：只改测量，不改游戏数据。后续的机制（051）和数值 spec 都要拿这里的基线做验收。

设计全文（指标定义、原型、目标值、人类试玩时间线）见该文档第 1、3、4 节，**数字照抄**，有出入以设计文档为准并在汇报里指出。

## 0. 文件边界（硬性）
- **可以改**：`scripts/balance/`、`scripts/playtest/`（新增遥测脚本放这里）、`eval/balance/`、`eval/reports/`、`tests/`（只新增文件；已有的 `test_balance*.py` 等只在不得不改时做最小修改，并在汇报里说明）。
- **不得改**：`host/`、`host/prompt/processed/` 下的剧本包、`scripts/scenario/`、`client/`。另一条工程线（047，难度模式）正在改这些地方。需要游戏侧才能解决的缺口，列进汇报，不要自己动。
- 既有工具的行为不能变：`python -m scripts.balance.sim --check`、`route`、`class_aware` 等在同一 seed 下的输出必须和改动前一致（新增东西走新模块或新参数，默认关闭）。动手前先对一两条既有命令存一份基线输出，改完逐字比对。
- EXP 等级制、新技能、被动二选一、冷却、状态效果**都还没有实装**。模拟按现状跑；凡是依赖这些的指标，接口和数据结构先留好，现状下返回 `not_applicable`（见第 3 节），不要伪造数据。

## 1. 玩家原型（路线级，只跑确定性引擎）
新增 `scripts/balance/archetypes.py`（原型定义，纯数据加少量规则）和 `scripts/balance/route_v2.py`（跑法与汇总），尽量复用 `class_aware.Run`、`checkpoints.replay_step`、`sim.choose_action`，不重写战斗引擎。原型来自设计文档 3.1：

| 原型 | 行为 | 通关率目标（草案，只做报告与门槛检查，不调数据） |
|---|---|---|
| P0a 零交互 | 只做推进主线必需的行动；不和 NPC 搭话、不购物、不带同伴、不用线索；被迫的战斗照打；战斗掉落自动拾取；战斗中反复用期望伤害最高的零成本行动；HP < 30% 用回复 | ≤ 5%（魔法使い ≤ 15%） |
| P0b 少量交互 | P0a + 最多 3 次可选交互（买一件被明确提示的商品、借一个免费同伴、听国王的提示）；拿到的装备会装上（含氷鉄の大剣）。**就是本次试玩者** | ≤ 5%（魔法使い ≤ 15%） |
| P1 普通 | P0b + 主线路过的支线，不追线索链 | 15–35% |
| P2 准备 | P1 + 设计中的关键准备链（见第 3 节 M2 的准备清单） | 55–75% |
| P3 全收集 | 全部支线和商店 | ≥ 80% |
| P2s 绕路型 | P2，但能绕开的战斗全部绕开 | 与 P2 通关率差 ≤ 10pp，到各节点的等级差 ≤ 1 |
| P0g 莽夫＋刷级 | P0b + 把所有可重复战斗刷到资源允许的极限 | 只报告，不设门槛；另报告"每升 1 级的期望资源消耗" |

要求：
- 原型 = 一组显式参数（允许的可选交互集合、同伴规则、装备规则、购物规则、支线集合、战斗策略、休息规则、回复阈值），写成数据表，加新原型或改参数不需要改跑法。休息规则按人类试玩复现（精霊の泉休息 3 次），具体怎么定在汇报里写清。
- **"通关"的默认定义：击败邪竜イグニス（进入 `defeated_ignis`）。**同时报告到达终局（`draco_battle` 或任一结局）的比例作为次要数字。定义以常量放在一个地方，方便设计负责人改。
- 战斗策略新增 `best_free`（"每回合用期望伤害最高的零成本行动，HP < 30% 用回复"）；P0 用它。加在 `sim.py` 的策略表里，现有策略的输出不变。
- **预留扩展点**（现状下用占位实现，写清接口和测试）：
  - `LevelModel`：现为"主线里程碑升级"；将来换成 EXP 驱动。每个原型要**记录到达各主线节点时的等级**。
  - `PassivePicker`：被动二选一的选择策略（固定规则：P0 取第一项，P2 取"该战斗更优"，另有"穷举全部组合"模式用来查死选项）。现状无被动，返回空。
  - 状态效果、技能冷却：战斗摘要里预留 `statuses`、`skill_usage` 字段，现状为空。
- 每个原型、每个职业（勇者、僧侶、魔法使い、盗賊）都跑，N 默认 500，seed 沿用 `sim.trial_seed` 的规则，可复现；支持多进程（沿用 `--workers`）。

## 3. 指标 M1–M13
新增 `scripts/balance/metrics_v2.py`，每个指标一个函数，输入统一的试验记录，输出 `{id, value, target, status}`，`status` 取 `pass` / `fail` / `report`（无门槛）/ `not_applicable`（依赖未实装机制，写明原因）。定义与目标见设计文档 3.2，**硬门槛是 M1、M3、M4、M9**，其余先报告。

| 编号 | 数据来源提示 |
|---|---|
| M1、M1' | 第 1 节各原型的通关率；相邻差 ≥ 15pp |
| M2 | 在目标遭遇上"全准备"与"全准备去掉 k"的胜率差。**准备清单**放 `eval/balance/preparations.json`（遭遇 → 准备项 → 如何从模拟里移除），由你按剧本提议，状态标 `proposed`，设计负责人定稿。起步：イグニス（紅玉の護符、アダマンタイトの鎧、聖水净化路线、氷鉄の大剣、火コウモリ竜及其强化） |
| M3、M3' | 每回合期望回复 ÷ 每回合期望受到伤害；玩家杀敌回合 ÷ 资源耗尽回合 |
| M4 | 任何策略下 Boss 回合数中位数；> 18 判沙袋战 |
| M5 | P1 到达最终 Boss 时的库存回复、回复道具使用率、未花金币占比 |
| M6 | Boss 战玩家用得最多的行动占比 |
| M7 | crucial 判定成功/失败两个分支的通关率差或资源差 |
| M8 | 每个同伴 × 每个 Boss 的胜率提升（上下限） |
| M9、M10、M11 | 复用并扩展 `budget.incoming_damage_budget`：每回合期望伤害 ÷ 最大 HP、每回合伤害 CV、战斗期望 HP 损失 ÷ 最大 HP（计入敌人存活时间，不计回复）。设计文档 1.6 的表是对照值，应能复现 |
| M12 | 技能回合占比、单技能占比、死选项——现状 `not_applicable` |
| M13 | 等级边际：现状能用"checkpoint 等级 ±1"探针就做，做不了就 `not_applicable`，并写明缺什么 |

## 5. 人类试玩存档遥测
- 新增 `scripts/playtest/save_telemetry.py`：输入一个存档 JSON（可选再给 `debug/traces/*.jsonl`、`debug/completions/`），输出 JSON + Markdown 报告到 `eval/reports/`：
  - 每场战斗：遭遇 ID、类别、回合数、结束 HP、玩家行动分布；
  - 回复道具的获得与使用；金币获得与花费；
  - 判定：次数、成功率、失败的代价；
  - 装备变更次数；关键准备（`preparations.json`）的拿到率与使用率；
  - 到达各 Boss 时的 HP、库存回复、等级；
  - 最后把该玩家放进 P0–P3 旁边比较，判断最接近哪个原型。
- 存档里能提取的信息有限（`event_log`、`dice_log`、`messages`、`system_logs`、`last_combat_result` 等）。**先把目标存档里实际有什么列出来**；缺的字段（例如每场战斗的完整行动记录）列成"需要引擎侧补记录"的清单放进汇报，由设计负责人决定，**不要自己改 `host/`**。
- 目标存档：人类试玩存档 `e2b9fdd9…`，按前缀在 `dist/LocalTRPG/saves/` 和 `host/saves/` 里查找。**撰写本 spec 时两处都没有这个前缀**（`host/saves/` 里只有 `e2b3…`、`e2b8…`、`e2b96f20…`，其中 `e2b96f20…` 是 Lv1 的空存档）。若你也找不到：不要去猜别的存档当作它，改为——脚本用合成存档做单元测试，复现基线（第 6 节）改用设计文档 1.1 的时间线表（9 场战斗的回合数和结束 HP）和 1.2 的资源清单作为参照，并在汇报里写明"未取得原始存档"。

## 6. 验收：先复现本次试玩
对**当前数据**跑出基线，必须满足（设计文档 A.4）：
1. **P0b 勇者通关率 > 90%。**
2. **イグニス战约 19 回合**（人类实测 20；模拟的中位数在 17–22 视为复现）。
3. **强化火コウモリ竜同伴下，M3 的 S > 1**（回复覆盖率；设计文档 1.4 的估算 +1.2/回合）。
4. 设计文档 1.6 的威胁表能被 M9/M10 复现：每回合期望伤害 ÷ 最大 HP 与表中数值相差不超过 2 个百分点，CV 相差不超过 0.1；超出的逐项解释原因。

复现不了就先修测量，不要往下做别的；修不了停下来汇报。基线结果写入 `eval/reports/046-measurement-v2-baseline.json` 和同名 `.md`（表格：原型 × 职业 × 通关率；M1–M13 状态；与设计文档目标的差距）。

## 7. 不做什么
- 不改游戏数据、不改 `host/`、不改剧本、不调任何数值（包括 `targets.json` 里的草案数字之外的"帮设计定数"）。

- 不联网，不调用任何 LLM。
